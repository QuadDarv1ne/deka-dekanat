# Деплой прототипа «Дека»

Требование конкурса: прототип открывается из России без VPN и работает до объявления итогов (28 ноября). Ниже два проверенных пути — выберите один.

Перед любым деплоем создайте свой `.env`:

```bash
cp .env.example .env
openssl rand -hex 32          # вставьте результат в AUTH_SECRET
```

> **Самодостаточный старт.** `npm start` запускает `scripts/start-prod.mjs`, который
> работает в любой чистой среде (деплой-платформа, CI, голый VPS): сам задаёт
> `DATABASE_URL` абсолютным путём к `db/custom.db`, а если файла базы нет — применяет
> схему (`prisma db push`) и наполняет демо-данными. Переменные из окружения
> (например, `DATABASE_URL` в docker-compose) имеют приоритет. То же делает и
> `npm run build` — сборке база не нужна, все маршруты динамические.

## Путь 0 (самый быстрый): install.sh — одной командой

Загрузите код на сервер (git clone или scp папки без node_modules), затем из корня проекта:

```bash
bash install.sh                # приложение
bash install.sh --with-ollama  # приложение + локальная модель Ollama (без внешних AI-сервисов)
```

Скрипт сам: поставит Docker (если нет), создаст `.env` со случайным `AUTH_SECRET`,
соберёт и запустит контейнер, дождётся `/api/health` и напечатает адрес и тестовые
аккаунты. Существующий `.env` не перезаписывает; порт меняется так: `DEKA_PORT=8080 bash install.sh`.

## Путь 1 (рекомендуется): VPS + Docker — доступ из РФ стабилен

Подойдёт любой российский VPS от 1 vCPU / 1 ГБ RAM: Timeweb Cloud, Beget VPS, Selectel, VK Cloud. Ubuntu 22.04+.

1. **Установите Docker** на сервере (одна команда):

   ```bash
   curl -fsSL https://get.docker.com | sh
   ```

2. **Загрузите код** на сервер (git clone вашего репозитория или scp папки проекта без `node_modules`).

3. **Задайте секрет** в файле `.env` рядом с compose-файлом (docker compose читает его
   автоматически): строка `AUTH_SECRET=<ваш секрет>`. Секрет можно не задавать только
   для локального теста — тогда встанет заглушка из compose-файла.

4. **Соберите и запустите**:

   ```bash
   docker compose up -d --build
   ```

   При старте контейнер сам применит схему БД и наполнит базу демо-данными.

5. **Проверьте**: `http://IP_СЕРВЕРА:3000` открывает экран входа. Войдите `student1 / demo1234`.

6. **HTTPS (опционально, но лучше для жюри)**: если есть домен, поставьте Caddy:

   ```bash
   sudo apt install caddy
   sudo tee /etc/caddy/Caddyfile << 'EOF'
   ваш-домен.ru {
       reverse_proxy 127.0.0.1:3000
   }
   EOF
   sudo systemctl restart caddy
   ```

   Caddy сам получит сертификат Let's Encrypt.

**Обновление прототипа**: `git pull && docker compose up -d --build` (или настройте автодеплой — см. ниже).

**Резервная копия базы**: `docker compose cp deka:/app/db/custom.db ./backup.db` — или через интерфейс (см. «Резервные копии и восстановление» ниже).

**Бонус**: на работающем сайте есть публичная страница `/download` — архив проекта
можно скачать прямо из браузера по ссылке `https://ваш-домен/download`, без репозитория.

### Готовый Docker-образ (после первого релиза)

Если публиковали репозиторий на GitHub — образ можно не собирать: пушьте тег,
и Actions соберёт его за вас:

```bash
git tag v1.6.0 && git push origin v1.6.0
```

Workflow `.github/workflows/release.yml` соберёт образ `ghcr.io/ВАШ_ЛОГИН/deka-dekanat`
(теги `1.6.0`, `1.6`, `latest`) и приложит zip/tar.gz архивы исходников к GitHub Release.
После этого новый сервер поднимается без клонирования репозитория:

```bash
docker run -d --name deka -p 3000:3000 -v deka-db:/app/db \
  -e AUTH_SECRET=$(openssl rand -hex 32) \
  ghcr.io/ВАШ_ЛОГИН/deka-dekanat:latest
```

### Автодеплой с GitHub на свой VPS

Репозиторий содержит шаблон `.github/workflows/deploy.yml.example`: переименуйте его в
`deploy.yml`, добавьте секреты `SSH_HOST`, `SSH_USER`, `SSH_PRIVATE_KEY` (Settings → Secrets → Actions) —
и каждый push в main будет сам обновлять сервер (`git pull` + `docker compose up -d --build`).
Сервер остаётся полностью вашим: никакого облака платформы, код, база и ключи — на вашей машине.

### Полностью автономный стек с локальной LLM (без внешних AI-сервисов)

Если университет не хочет отправлять даже обезличенные запросы во внешний AI-сервис,
поднимите модель у себя — файл `docker-compose.ollama.yml` добавляет к приложению
Ollama с русскоязычной моделью (по умолчанию `qwen2.5:3b-instruct`, ~2 ГБ, работает даже без GPU):

```bash
docker compose -f docker-compose.ollama.yml up -d --build
docker compose -f docker-compose.ollama.yml logs -f ollama-init   # ждать «Модель готова.»
```

Приложение автоматически переключится на `LLM_BASE_URL=http://ollama:11434/v1`
(режим «свой OpenAI-совместимый провайдер») — персональные данные студентов не покидают
контур вуза. Без этой конфигурации ассистент работает через обычный `docker-compose.yml`
или во встроенном офлайн-режиме.

## Путь 2: Railway / Render (быстро, но проверьте доступность из РФ)

Обе платформы умеют Next.js + Docker.

**Railway:**
1. New Project → Deploy from GitHub repo.
2. Variables: `AUTH_SECRET` (ваш секрет), `DATABASE_URL=file:/app/db/custom.db`.
3. Railway соберёт по Dockerfile; включите persistent volume на `/app/db`, иначе база обнуляется при рестарте.

**Render:**
1. New → Web Service → подключите репозиторий (Environment: Docker).
2. Environment: те же переменные. Add Disk: mount `/app/db`, 1 GB.
3. Health check path: `/`.

⚠️ Доступность этих платформ из России зависит от провайдера — обязательно проверьте ссылку с мобильного оператора (МТС/Мегафон) без VPN. Если открывается нестабильно — используйте Путь 1.

## Резервные копии и восстановление

Прототип даёт деканату полный контроль над данными — несколько взаимодополняющих способов:

**1. Логический бэкап через интерфейс (рекомендуется).** Кабинет деканата → Профиль →
«Суверенитет данных деканата»:

- **«Полный бэкап (JSON)»** — скачивает всю базу одним файлом `deka-backup-<дата>.json`:
  пользователи и пароли (bcrypt-хеши), расписание с переносами, заявки с полной историей
  статусов, оценки, экзамены, объявления, уведомления. Только для сотрудников деканата.
- **«Восстановить из файла»** — заменяет содержимое базы содержимым копии. Перед записью файл
  проверяется (формат, целостность связей), сама замена идёт в одной транзакции: при любой
  ошибке база остаётся прежней. Требует явного подтверждения в диалоге.

Формат копии (`deka-backup`) — обычный читаемый JSON: его можно открыть в редакторе,
передать по почте/мессенджеру, положить в облако вуза — данные не привязаны к инсталляции.

**2. Файловый снапшот на сервере.** SQLite-база — один файл, поэтому «холодная» копия
делается мгновенно:

```bash
npm run db:snapshot                 # db/snapshots/deka-<штамп>.db, хранятся последние 20
# восстановление: остановить приложение, затем
cp db/snapshots/deka-<штамп>.db db/custom.db
# в Docker: docker compose cp deka:/app/db/custom.db ./backup.db
```

**3. Восстановление из командной строки — без работающего приложения.** Если сервер
не поднимается (сбой, откат версии) и UI недоступен, база всё равно восстанавливается
из JSON-копии:

```bash
npm run db:restore -- db/deka-backup-2025-11-20.json     # спросит подтверждение REPLACE
npm run db:restore -- db/deka-backup-2025-11-20.json --yes   # для скриптов/автоматизации
```

Перед заменой скрипт валидирует файл (формат `deka-backup`, структура, связи), делает
страховочный снапшот текущей базы в `db/snapshots/deka-pre-restore-<штамп>.db` и только
потом заменяет данные в одной транзакции: id и bcrypt-хеши паролей сохраняются.
Нужны установленные зависимости (`npm install`) — на Docker-сервере для этого случая
используйте файловый способ из п. 2 (`docker compose cp`).

**4. Мониторинг живости.** `GET /api/health` — публичная точка без персональных данных:
`{"ok":true,"db":"ok","version":"…"}` (HTTP 503, если база недоступна). Тот же эндпоинт
использует Docker-healthcheck: контейнер с неработающей базой честно помечается unhealthy.

### Перенос на другой сервер за 5 минут

1. На старом сервере: кабинет деканата → «Полный бэкап (JSON)» (или `npm run db:snapshot`).
2. На новом сервере: установить Docker, забрать код (`git clone` или scp папки), задать свой `AUTH_SECRET`.
3. `docker compose up -d --build` — приложение поднимется с демо-данными.
4. Войти как сотрудник деканата → «Восстановить из файла» → выбрать копию из п. 1.
   Все аккаунты, заявки, история и расписание вернутся 1:1 (id и даты сохраняются).
5. Переключить домен/DNS на новый сервер. Старый можно выключить.

Пароли пользователей при переносе сохраняются (переносятся bcrypt-хеши), сессии
перевыпускаются автоматически — JWT подписан `AUTH_SECRET` нового сервера.

## Масштабирование на будущее

Прототип работает на SQLite — для конкурса этого достаточно (сотни одновременных просмотров жюри SQLite держит спокойно, чтения идут из одного файла, записи редкие).

Архитектура готова к росту:
- **Prisma ORM** — переезд на PostgreSQL = заменить `provider = "sqlite"` на `"postgresql"` в `prisma/schema.prisma`, поменять `DATABASE_URL` и выполнить `prisma db push`. Код приложения не меняется.
- **Next.js standalone** — контейнер горизонтально масштабируется за балансировщиком (Nginx/Caddy).
- **Сессии — JWT** (без серверного хранилища) — любой инстанс обслуживает любого пользователя.
- Для многотысячной нагрузки: вынести БД в управляемый Postgres, добавить Redis для rate-limit логина и кэша расписания.

- [ ] Входят все три аккаунта: `student1`, `student2`, `dekanat` (пароль `demo1234`)
- [ ] Студент видит только свои заявки и оценки (проверено: чужие данные по API не отдаются)
- [ ] `AUTH_SECRET` на сервере отличается от примера в `.env.example`
- [ ] В коде нет ключей ИИ-сервисов: ключ подаётся переменной окружения на сервере (или используется локальная модель — см. docker-compose.ollama.yml)
- [ ] На сайте есть плашка «концепт для конкурса, не официальный сервис»
- [ ] Репозиторий открыт для жюри (или архив на Яндекс Диске)
- [ ] Офлайн-режим: выключите сеть на телефоне — разделы показывают сохранённый слепок данных, баннер «Автономный режим» виден
